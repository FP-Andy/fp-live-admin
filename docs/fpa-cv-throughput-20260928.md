# AWS FPA 처리 속도 점검

## 측정 조건과 원인

- 기존 g4dn.xlarge / Tesla T4, 4 vCPU. 실제 실행 중 GPU 사용률 8%, FPA CPU 약 172%, 하이라이트 워커 0%였다.
- 동일한 업로드 원본, 작업자가 저장한 코트·색상·13명 설정, YOLO26s, 1280 입력, confidence 0.1, 초당 약 15샘플을 유지했다. 전체 분석은 중지하고 서로 간섭하지 않도록 짧은 구간을 비교했다.
- 3초 구간 cProfile: 색상 추출 15.886초, YOLO predict 2.337초, 영상 읽기 1.208초, 미리보기 쓰기 0.757초. 프로파일링에는 측정 오버헤드가 있으므로 아래 실제 속도 비교와 구분한다.
- 색상마다 픽셀 배열 전체를 다시 골라 평균을 구하는 반복과, 중복 검출 제거/팀 할당에서 같은 색상 분류를 두 번 호출하는 것이 주요 병목이었다.

## 적용한 변경

RGB 512구간의 개수와 채널 합을 `bincount`로 한꺼번에 계산한다. 원본 픽셀, 배경 제거, RGB 반올림, 가중치, 판정 임계값을 그대로 유지한다. 같은 검출의 분류 결과를 중복 제거와 팀 할당이 공유한다.

모델, 정밀도, 검출 해상도, 분석 FPS, 코트 범위, 트래커 기준, 미리보기 품질은 변경하지 않았다. 특정 경기·선수·트랙·색상에 대한 하드코딩은 없다.

## 결과

동일한 5초 구간 / 75개 분석 프레임, 프로파일러 없이 별도 프로세스로 측정:

| 항목 | 기존 | 적용 코드 |
| --- | ---: | ---: |
| 추적·미리보기 처리 | 32.352초 | 16.596초 |
| 처리량 | 2.318프레임/초 | 4.519프레임/초 |
| 프로세스 전체 | 37.168초 | 21.500초 |

약 1.95배 개선. 모든 분석 프레임의 좌표, 트랙 ID, confidence, 색상 표현, 트랙 요약이 정확히 같았다. 무작위 RGB·경계값·비연속 배열의 히스토그램도 기존 평균과 정확히 일치했다. 색상·팀 분류·트래커 회귀 검사를 실행했다.

추가 색상 거리 캐시는 같은 구간에서 4.37프레임/초로 실익을 확인하지 못해 적용하지 않았다.

전체 13,645프레임을 4.519프레임/초로 환산하면 약 50분이다. 짧은 구간을 이용한 추정이므로 전체 경기 처리 시간으로 보장하지 않는다. CPU 색상 처리를 줄였지만 영상 디코딩·색상 처리·추론·미리보기의 직렬 실행은 남아 있다. 여러 단계를 겹쳐 실행하는 구조와 배치 추론은 별도 정확도 검증이 필요하다.

## 단계 병렬화 — 추가 적용

CUDA 실행에서 영상 읽기·미리보기, YOLO 검출, 검출 박스의 색상 분석을 겹쳐 실행한다. 각 단계의 큐는 2개로 제한한다. 색상 분석은 CPU 프로세스 하나로 분리하고, 공유 메모리에 한 프레임만 복사해 전달한다. 원본 영상을 프로세스마다 읽거나 대용량 프레임을 매번 직렬화하지 않는다. 다음 프레임 복사는 이전 색상 응답을 받은 뒤에만 진행한다.

중복 박스 제거, ByteTrack 갱신, 수동 팀 시드 적용, 최종 박스의 색상 추출은 원래 프레임 순서를 지킨다. 모델·정밀도·샘플링·판정은 그대로다. CPU/MPS는 기존 순차 실행을 유지한다. CUDA의 `--serial`은 진단용 순차 비교, `--threaded-colors`는 색상 프로세스 없이 스레드만 사용하는 비교 옵션이다. 단계별 처리 시간은 프로세스 로그에 남긴다. 이 시간들은 서로 겹치므로 합산한 값을 전체 소요 시간으로 해석하면 안 된다.

같은 T4 / 4 vCPU에서 진행 중 분석을 취소한 뒤, 각 버전을 순차 실행했다. 각 구간은 150개 분석 프레임이다. 첫 구간은 사용자가 저장한 초기 설정부터 10초, 두 번째는 30–40초를 독립 실행했다.

| 비교 구간 / 방식 | 추적 시간 | 처리량 | 프로세스 전체 |
| --- | ---: | ---: | ---: |
| 초기 구간 / 직렬 기준 `df66211` | 31.484초 | 4.764 fps | 36.551초 |
| 초기 구간 / 스레드만 분리 | 28.458초 | 5.271 fps | 33.533초 |
| 초기 구간 / 색상 프로세스 + 단계 병렬화 | 24.622초 | 6.092 fps | 29.532초 |
| 30–40초 / 직렬 기준 | 33.006초 | 4.545 fps | 38.359초 |
| 30–40초 / 색상 프로세스 + 단계 병렬화 | 26.027초 | 5.763 fps | 31.491초 |

직렬 기준 대비 추적 시간 약 21–22% 감소, 처리량 약 27–28% 증가. 프로세스 전체에는 모델 준비·영상 탐색·인코더 마무리도 포함한다. 두 구간 모두 `frames`, `tracks`, `video`, `detector` JSON이 정확히 일치했다. 무작위 run UUID는 비교 대상에서 제외했다. 미리보기는 기존과 동일한 H.264 / 1920×1080 / 30000:1001 FPS이며 전체 디코딩에 성공했다. 첫 구간은 300프레임, 두 번째는 원본 프레임 경계에 따라 299프레임이며 각 기준 실행과 같다.

전체 13,645개 분석 프레임으로 환산하면 약 37–40분이다. 전체 경기 완료 시간을 실측한 수치는 아니며 장면과 CPU 부하에 따라 달라진다. 단일 경기 내 단계 병렬화이며, 여러 경기를 동시에 실행하는 기능은 추가하지 않았다. 현재 워커의 4 vCPU가 남은 제약이다.

메모리 무한 적재 방지, 순서 보존, 검출/디코딩 오류 전달, 소비자 중단, 별도 프로세스 색상 결과 일치, 공유 메모리 해제와 기존 회귀 검사 43개를 AWS에서 통과했다. SIGTERM을 받으면 단계와 색상 프로세스·미리보기 인코더를 정리하며, 미완성 결과를 공개하지 않는다. GPU 컨테이너의 공유 메모리 한도를 256 MiB로 설정했다. 공유 메모리가 부족한 환경에서는 로그를 남기고 같은 색상 함수를 프로세스 내부에서 수행한다.
