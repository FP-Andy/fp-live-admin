# FP Live Admin Design Principles

## 목적
이 문서는 외부 디자인 시스템 초안을 그대로 복사하지 않고, `FP Live Admin`의 실제 운영 환경에 맞게 번역한 실전 디자인 원칙이다.

우리가 만드는 화면은 일반 백오피스가 아니라, 라이브 경기 운영과 스트림 제어를 빠르게 판단해야 하는 콘솔이다.
따라서 "예쁜 다크 테마"보다 아래 세 가지를 우선한다.

- 상태가 한눈에 읽혀야 한다.
- 위험 액션과 일반 액션이 명확히 구분돼야 한다.
- 정보가 많아도 긴장 상황에서 침착하게 읽혀야 한다.

---

## 1. Creative Direction
우리 서비스의 디자인 방향은 아래 한 줄로 정의한다.

**"Calm Live Operations Console"**

핵심 해석:

- 라이브 데이터는 떠오르고, 나머지 UI는 뒤로 물러나야 한다.
- 화면은 화려하기보다 정제되어야 한다.
- 관리자 화면이 아니라 방송/운영 장비 같은 신뢰감을 줘야 한다.

즉, "에디토리얼 무드"는 일부 참고하되, 최종 결과는 항상 **운영 효율과 판단 속도**를 높이는 쪽이어야 한다.

---

## 2. Surface Rules
### 2-1. 기본 원칙
- 검은색 `#000000`은 쓰지 않는다.
- 다크 테마는 깊이 있는 브라운-차콜 기반으로 유지한다.
- 섹션 구분은 가능한 한 **강한 선**보다 **톤 차이와 여백**으로 만든다.

### 2-2. Border 사용 원칙
- 1px 실선 남용은 금지한다.
- 완전 무경계도 금지한다.
- 입력창, 위험 액션, 포커스 상태처럼 명확한 구분이 필요한 곳만 약한 ghost border를 사용한다.

권장 해석:

- 카드/레이아웃 구획: 배경 톤 차이 + spacing
- 입력 필드/버튼/위험 영역: 저대비 border 허용
- 표/리스트 구분: 선 대신 gap, hover surface shift, 혹은 매우 약한 dashed divider 사용 가능

### 2-3. 계층 구조
화면의 표면은 아래처럼 계층을 가진다.

- `Base`: 앱 전체 배경
- `Structural`: sidebar, topbar, layout frame
- `Workspace`: 각 페이지의 주 작업 영역
- `Card`: 개별 정보 블록
- `Floating`: dropdown, toast, floating control

핵심은 모든 카드가 똑같이 보이지 않게 하는 것이다.
페이지에서 가장 중요한 블록만 한 단계 더 떠 보여야 한다.

---

## 3. Color Strategy
### 3-1. 역할 분리
현재 오렌지 계열은 브랜드 중심 강조색으로 유지한다.
하지만 모든 강조를 오렌지로 통일하지 않는다.

- `Primary / Brand`: warm orange
- `Success / Running`: green
- `Warning / Attention`: amber
- `Danger / Destructive`: red
- `Technical / Telemetry`: cool cyan or blue

### 3-2. 적용 원칙
- 브랜드 CTA, 활성 필터, 핵심 섹션 강조는 오렌지
- running/live 상태는 green
- HLS probe, ping, bitrate, gateway 상태 같은 기술 정보는 cyan 계열
- danger action과 오류는 red

이렇게 해야 같은 "강조"라도 의미가 달라진다.

### 3-3. 금지
- 모든 상태를 오렌지로 처리하지 않는다.
- pure white 텍스트를 넓게 쓰지 않는다.
- 너무 밝은 네온을 전체 화면에 뿌리지 않는다.

---

## 4. Typography
### 4-1. 기본 원칙
- 타이포는 장식보다 **정보 위계**를 만드는 도구다.
- 제목, 수치, 메타 정보의 차이를 더 크게 벌린다.

### 4-2. 권장 구조
- 페이지 제목: 가장 크고 강하게
- 섹션 제목: 짧고 분명하게
- KPI 수치: 크고 압축감 있게
- 메타 정보: 작고 옅게
- 설명문: 최소화

### 4-3. 실제 적용 기준
- 대시보드의 숫자, 라이브 상태, 매치 이름은 지금보다 더 강하게
- helper text와 설명 문장은 지금보다 더 줄이기
- 기술 메타는 작은 텍스트로 정리하되, 색상으로 의미 구분하기

---

## 5. Spacing & Density
### 5-1. 원칙
운영툴은 정보가 많아도 "숨 쉴 구간"이 있어야 한다.

- 큰 섹션 간격은 분명하게
- 반복 리스트는 더 촘촘하게
- 중요한 카드만 여백을 넉넉하게

### 5-2. 실전 해석
- Hero/KPI/주요 패널은 여백을 더 크게
- 매치 리스트, 로그, 감사 이벤트는 조밀하게
- 설명 블록이 길어질수록 공간이 아니라 텍스트량을 줄인다

---

## 6. Components
### 6-1. Buttons
버튼은 용도별로 시각 무게가 달라야 한다.

- `Primary`: 가장 자주 쓰는 핵심 액션
- `Secondary`: 일반 조작
- `Ghost`: 필터, 보조 액션, 이동
- `Danger`: 삭제, 정지, 초기화

버튼 원칙:

- 모든 버튼을 pill 형태로 만들지 않는다.
- radius는 과하지 않게 통일한다.
- 위험 액션은 색과 위치 모두에서 일반 액션과 분리한다.

### 6-2. Status Indicators
상태는 텍스트보다 먼저 보여야 한다.

권장 상태군:

- `Running`
- `Stopped`
- `Archived`
- `Warning`
- `Manual`
- `Technical OK / Fail`

원칙:

- status pill은 유지 가능
- 단, 의미마다 색을 분리
- running 상태는 약한 glow 허용
- technical LED 같은 작은 시각 신호 도입 가능

### 6-3. Cards
카드는 모두 같은 중요도로 보이면 안 된다.

카드 유형:

- `Hero Card`: 핵심 KPI 또는 중요한 현재 상태
- `Panel Card`: 일반 작업 영역
- `Utility Card`: 보조 정보, 로그, 가이드

### 6-4. Inputs
- 입력창은 배경을 더 낮은 surface로
- border는 ghost 수준
- focus 상태에서만 primary 계열 강조
- helper text는 짧고 직접적으로

---

## 7. Layout Rules By Screen
### 7-1. Dashboard
목표:

- "지금 무엇이 중요한지"를 먼저 보여주는 화면

원칙:

- KPI와 Quick Create는 상단
- Match List는 메인 작업축
- Calendar는 보조
- 매치 카드에서는 이름, 상태, 담당자, 액션 순서가 빨리 읽혀야 한다

### 7-2. Match Control
목표:

- 복잡한 제어를 하더라도 패닉이 오지 않는 화면

원칙:

- 실시간 조작과 분석 입력을 분리
- 위험 액션은 별도 zone으로 분리
- 헤더만 봐도 현재 경기 상태를 파악할 수 있어야 함

### 7-3. Media
목표:

- 장비 상태판처럼 보이는 화면

원칙:

- gateway 상태, HLS probe, stream attach 문제를 빠르게 식별
- 각 매치 카드는 "기술 패널"처럼 구성
- 복구 액션과 중단 액션을 시각적으로 다르게

### 7-4. System
목표:

- 시스템 판단과 운영 안전 가이드를 제공하는 화면

원칙:

- overall health → alerts → guide → audit 순으로 읽히게
- warning과 info를 같은 톤으로 두지 않기
- 감사 로그는 차가운 정보 피드처럼 정리

---

## 8. Do / Don’t
### Do
- 상태와 액션 우선순위를 시각적으로 명확히 구분한다.
- 오렌지 외에 기술 메타용 차가운 색을 도입한다.
- 강한 border 대신 surface depth를 활용한다.
- 운영 화면답게 "빠른 판단"을 먼저 설계한다.

### Don’t
- 모든 카드, 버튼, 배지를 같은 톤으로 만들지 않는다.
- 설명문을 길게 써서 폼이나 카드가 문서처럼 보이게 하지 않는다.
- 라이브 운영 화면을 잡지형 에디토리얼 레이아웃으로 과하게 밀지 않는다.
- blur, glow, gradient를 전역적으로 남용하지 않는다.
