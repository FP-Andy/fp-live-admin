# FLA 기록 정정 규칙 (RULES) — 버전 2026-11-04.1

이 문서는 FPC 서버가 `GET /api/agent/fla/rules` 로 그대로 내보내는 정본이다. 서버는 여기 적힌 규칙을 **같은 내용으로 강제**한다
(규칙 밖 값은 plan 단계에서 422 로 거부된다). 에이전트는 이 문서에 있는 절차로만 고치고, 정해지지 않은 정정은 **"대표에게 문의"** 로 끝낸다.

## 0. 언제나 이 순서로

1. **읽기** — `get_match`(경기 상태·하프·라인업·점수) → `get_timeline`(기록 id·시각) 으로 지금 기록을 본다.
2. **모호하면 묻기** — 9장의 질문 중 답이 없는 것이 하나라도 있으면 먼저 직원에게 묻는다. 추측해서 채우지 않는다.
3. **plan** — 바꿀 내용을 ops 로 만들어 `plan_change`. 아무것도 바뀌지 않는다.
4. **직원 확인** — plan 결과의 `changes`(전/후), `score`(점수 전/후), `warnings` 를 그대로 보여 주고 "적용할까요?" 라고 묻는다.
   진행 중 경기에서 점수가 바뀌면(`LIVE_BROADCAST_SCORE`) **운영자와 말을 맞췄는지** 꼭 확인한다.
5. **apply** — 직원이 "적용" 이라고 답한 뒤에만 `apply_plan(plan_id)`. plan 은 10분 뒤 만료된다.
6. **확인** — `get_timeline`/`get_result` 로 바뀐 것을 확인하고, apply 응답의 `follow_ups` 중 `auto:false` 항목(직접 다시 해야 할 일)을 직원에게 알려 준다.
7. **되돌리기** — 잘못 고쳤으면 `revert_change(change_id)`. 그 뒤 같은 기록이 또 바뀌었으면 서버가 거부한다(그때는 지금 기록을 보고 새로 plan).

## 1. 시각 표기 (가장 중요)

- 모든 시각은 **하프 + 경기 시계**로 적는다: `{"half": "2H", "clock": "67:30"}`.
  - 하프: `1H`(전반) · `2H`(후반) · `ET1`(연장 전반) · `ET2`(연장 후반).
  - 경기 시계: 그 하프의 경기 시계 그대로. 후반은 45:00 부터(45분 하프 기준), 연장 전반은 90:00, 연장 후반은 105:00 부터 센다.
  - 추가시간: `"45+2:10"`(전반 추가 2분 10초) 또는 같은 뜻의 `"47:10"` 둘 다 된다. 후반은 `"90+3:00"` = `"93:00"`.
  - 하프마다 추가시간은 20분까지(예: 1H 는 `45+20:00` 까지).
  - 하프 길이는 경기마다 다르다(SUFA 20분 등). `get_match` 의 `halves` 를 보고 맞춘다.
- **영상 시각(유튜브·녹화 파일의 몇 분)은 받지 않는다.** 직원이 영상 시각만 알면 "경기 시계로 몇 분이었나요?" 라고 묻는다.
  모르면 `get_timeline` 에서 앞뒤 기록을 보여 주고 고르게 한다. 그래도 정할 수 없으면 대표에게 문의.
- 저장 값(`raw_clock_ms`)은 킥오프부터 시계가 실제로 흐른 누적 ms 다(쉬는 시간 제외).
  - 전반: 저장 값 = 경기 시계(ms). 전반 45+2:10 → 2,830,000.
  - 후반: 저장 값 = 후반 시작 표시(HALFTIME_START)의 저장 값 + (경기 시계 − 45:00).
  - 서버가 변환하므로 에이전트는 저장 값을 직접 넣지 않는다. 응답에는 `label`(예 `2H 67:30`)과 `raw_clock_ms` 가 함께 온다.
- ⚠️ **콘솔 기록 수정 화면(Event Editor)의 Clock 칸은 저장 값을 그대로 mm:ss 로 보여 준다**(경기 시계가 아님). 전반은 같지만, 후반 이후는
  전반 추가시간만큼 다르다(예: 전반이 45+2:00 에 끝난 경기의 후반 64:22 골이 수정 화면에는 66:22 로 보인다).
  직원이 수정 화면에서 본 시각으로 말하면, `get_timeline` 에서 `raw_clock_ms` 가 그 값인 기록을 찾아 경기 시계 label 로 다시 확인받는다.
- 시각은 그 하프 안이어야 한다. 다음 하프가 이미 시작된 시각을 넣으면 `CLOCK_IN_NEXT_PERIOD` 로 거부된다(하프를 다시 물어볼 것).
- 경기 시계 표시가 정규 시간을 넘으면 서버 응답은 `45+2:10`·`90+3:00` 처럼 적는다.

## 2. 팀 표기

- 저장 값은 `HOME` / `AWAY` 둘뿐이다. 한국어로는 **홈 / 어웨이**(원정)라고 말한다.
- 팀 이름 ↔ HOME/AWAY 는 `get_match` 의 `home_team`·`away_team` 으로 바꾼다. 직원이 팀 이름으로 말하면 그 표로 바꾸고, plan 결과에 팀 이름이 맞게 나오는지 확인한다.
- 경기 이름 꼴: `[대회 | 라운드R] 홈팀 vs 어웨이팀`.

## 3. 기록 종류와 필드

| 종류 | 저장 type | 필수 | 선택 | 허용값 |
|---|---|---|---|---|
| 슈팅(골·자책골 포함) | `XG` | team, at, shot_x, shot_y | xg(비우면 위치로 계산), is_on_target, is_goal, is_own_goal, player_number(+player_name), goalmouth_x/y, is_header, is_weak_foot, under_pressure, one_on_one, shot_pace_band | shot_x 52.5~105(공격 방향 기준 m, 상대 골라인 105), shot_y 0~68, xg 0~1, goalmouth 0~1, shot_pace_band LOW·MID·HIGH |
| 공격방향 | `ATTACK_LANE` | team, lane, at | — | lane LEFT(왼쪽)·CENTER(가운데)·RIGHT(오른쪽) |
| 하프 시작 표시 | 마커 `HALFTIME_START`·`EXTRA_TIME_1_START`·`EXTRA_TIME_2_START` | — | — | 하프마다 하나 |
| 점유 구간 | 점유 segment | team, 시작·끝 | — | team HOME·AWAY, 끝이 비어 있으면 "지금 열린 구간" |

- 슈팅 위치는 **늘 공격하는 쪽 반 코트 기준**으로 저장된다(전·후반 진영 바뀜과 무관). 직원이 위치를 모르면 묻는다. 끝까지 모르면 대표에게 문의(위치 없이 슈팅을 만들지 않는다).
- 등번호(player_number):
  - 그 팀 라인업이 있으면 **라인업에 있는 번호만** 된다. 없으면 `NUMBER_NOT_IN_LINEUP`(라인업 번호 목록이 함께 온다). 라인업 자체가 틀렸으면 대표에게 문의.
  - 이름은 라인업에서 자동으로 채운다. 이름을 주면 라인업 이름과 같아야 한다(`NAME_MISMATCH`).
  - 라인업이 없는 팀이면 경고(`NO_LINEUP`)와 함께 받은 값 그대로 저장한다.
  - 이름만 있고 번호가 없으면 넣지 않는다(`NAME_WITHOUT_NUMBER`). 선수를 비우려면 `clear_player: true`.
- 기록 수정 화면과 같은 함수로 저장하므로 xGOT(유효슈팅 기대값)는 서버가 다시 계산한다.

## 4. 골 · 자책골 · 유효슈팅 · 점수

- **점수 = 그 팀의 `XG` 기록 중 `is_goal=true` 인 것의 개수.** 다른 것으로는 점수가 바뀌지 않는다.
- 골(`is_goal=true`)은 반드시 유효슈팅(`is_on_target=true`)이고 골문 도착 위치(goalmouth_x·goalmouth_y)가 있어야 한다.
  유효슈팅도 골문 도착 위치가 필요하다(`GOALMOUTH_REQUIRED`). 유효슈팅이 아니면 도착 위치는 지운다.
- 자책골(`is_own_goal=true`): **team 은 점수를 얻은 팀**이다(상대 선수가 자기 골문에 넣은 경우, 점수를 얻은 쪽 팀).
  서버가 자동으로 is_goal=true · is_on_target=false · xg=0 · 선수 없음 · 도착 위치 없음으로 맞춘다. 자책골은 그 팀 슈팅 수·xG 에 들어가지 않는다.
- 골을 하나 지우거나 골→슈팅으로 바꾸면 그 팀 점수가 1 줄고, 슈팅→골이면 1 는다. 득점 팀을 바꾸면 한 팀 −1, 다른 팀 +1.
  plan 결과의 `score.before → score.after` 로 꼭 확인한다.
- 방송 점수판이 **수동 점수**를 쓰는 경기면(`BROADCAST_MANUAL_SCORE`), 기록을 고쳐도 점수판은 안 바뀐다 — 운영자가 점수판 점수를 직접 맞춰야 한다고 알린다.

## 5. 공격방향 · 점유 · 하프 시작 표시

- 공격방향 기록은 "그 시각에 그 팀이 어느 쪽으로 공격했는가" 한 번의 기록이다. 바꿀 수 있는 것은 시각·팀·방향뿐.
- 점유 구간은 연속된 구간들이다(앞 구간의 끝 = 뒤 구간의 시작, 공이 아웃된 시간은 빈칸).
  - 팀이 반대로 찍힌 구간: `set_possession_team(segment_id, team)`.
  - 점유 버튼을 늦게/일찍 눌렀다: `move_possession_boundary(segment_id=앞 구간, new_end)` — 앞 구간의 끝과 바로 뒤 구간의 시작이 함께 옮겨진다.
  - **열린 구간(끝이 비어 있음)과 그 경계는 고치지 않는다** — 지금 점유는 운영자가 매치 컨트롤에서 바꾼다.
  - 구간 지우기·전체 초기화는 할 수 없다(대표에게 문의).
- 하프 시작 표시: `set_period_start(period, previous_period_clock)` — 예: 후반 시작 = 전반 시계가 `45+2:30` 이었을 때.
  - 표시를 옮기면 **저장 값은 그대로이고 표시만 바뀐다**: 경계 근처 기록의 하프가 바뀌고, 그 하프 기록 전체의 경기 시계가 같은 만큼 밀린다. plan 의 `PERIOD_SHIFT` 경고에 몇 건이 어떻게 바뀌는지 예시가 나온다 — 직원과 같이 확인한다.
- 시각 일괄 이동: `shift_events(half, from_clock, to_clock, delta_seconds)` — 그 범위의 슈팅·공격방향 기록 저장 시각을 ±초만큼 옮긴다(±300초 이내, 하프 밖으로 나가면 거부). 점유 구간은 같이 옮기지 않는다.

## 6. 진행 중 경기(보관 전)

- 진행 중 경기도 고칠 수 있다. 단 **운영자의 실시간 입력을 깨지 않는 범위**만 된다.

| 진행 중에 | 결과 |
|---|---|
| 이미 지나간 슈팅·골·자책골·공격방향 추가·수정·삭제 | 된다 |
| 지금 시계보다 뒤의 시각 | 거부 `LIVE_FUTURE_TIME` |
| 방금(30초 안에) 들어온 기록 수정·삭제 | 거부 `LIVE_TOO_RECENT` — 30초 뒤 다시 plan |
| 닫힌 점유 구간의 팀·경계 | 된다(지금 시계 이전만) |
| 열린 점유 구간, 지금 점유 바꾸기 | 거부 — 운영자 몫 |
| 이미 있는 하프 시작 표시 옮기기 | 된다(지금 시계 이전만) |
| 하프 전환(새 하프 시작 표시) | 거부 `LIVE_PERIOD_TRANSITION` — 운영자 몫 |
| 경기 시계 시작·정지·맞추기 | 할 수 없음 — 운영자 몫(시계가 몇 초 틀렸으면 7-G 절차) |
| 경기 이름(팀 이름) | 거부 `LIVE_RENAME` — 보관 뒤에 |

- 진행 중 수정은 **방송에 바로 나간다**: 점수판·오버레이 3초 안, 중계 그래픽 PNG 는 다음 60초 갱신 때.
  - **점수가 바뀌는 수정은 운영자와 말을 맞춘 뒤 apply 한다.** plan 에 `LIVE_BROADCAST_SCORE` 가 있으면 직원에게 "운영자에게 알렸나요?" 를 묻고, 답을 받은 뒤에만 apply.
  - 운영자 화면에는 "OOO님이 기록을 고쳤습니다(무엇·몇 분)" 알림이 뜬다.
- plan 뒤에 운영자가 새 기록을 넣는 것은 정상이다. **고치려는 기록이 그대로면 apply 된다.** 고치려던 기록이 바뀌었거나(`stale_plan`), 넣으려는 기록과 겹치는 새 입력이 생겼으면(`new_input_clash`) 거부되니 다시 plan 한다.
- 에이전트가 지운 기록은 운영자 화면이 같은 기록을 다시 보내도 되살아나지 않는다.

## 7. 자주 생기는 정정 — 정해진 절차

각 절차: **확인할 것 → op → plan 결과에서 볼 것**. 직원 확인 없이 apply 하지 않는다.

### A. 골 시각이 잘못 들어갔다
- 확인: 어느 골인지(득점 팀·선수·지금 기록된 시각), 맞는 하프와 경기 시계.
- op: `update_event(event_id, set={"at": {"half": "2H", "clock": "67:30"}})`
- 볼 것: changes 의 전/후 시각, 점수는 그대로여야 함. `CLOCK_IN_NEXT_PERIOD` 면 하프를 다시 묻는다.

### B. 득점 팀이 반대로 들어갔다
- 확인: 실제 득점 팀, 득점 선수 등번호(새 팀 라인업 기준). 자책골인지.
- op: `update_event(event_id, set={"team": "AWAY", "player_number": "9"})` — 선수를 모르면 `"clear_player": true`.
  자책골이었다면 `set={"is_own_goal": true, "team": "점수를 얻은 팀"}`.
- 볼 것: score 가 한 팀 −1·다른 팀 +1. 슈팅 위치(shot_x·y)는 공격 방향 기준이라 팀만 바꿔도 된다.

### C. 등번호(선수)가 잘못 들어갔다
- 확인: 맞는 등번호. 라인업에 그 번호가 있는지(`get_match` 의 lineups).
- op: `update_event(event_id, set={"player_number": "10"})` — 이름은 라인업에서 자동.
- 볼 것: changes 의 선수 이름이 직원이 말한 사람과 같은지. `NUMBER_NOT_IN_LINEUP` 면 번호를 다시 묻고, 라인업이 틀렸다면 대표에게 문의.

### D. 빠진 슈팅(골)을 추가해야 한다
- 확인: 팀, 하프·경기 시계, 슈팅 위치(공격 방향 기준 x·y — 직원이 말한 위치를 숫자로 바꿀 때는 "페널티 박스 정면 = x 94, y 34" 처럼 확인받는다), 유효슈팅/골 여부와 골문 도착 위치, 선수 등번호.
- op: `add_shot(team, at, shot_x, shot_y, is_on_target, is_goal, goalmouth_x, goalmouth_y, player_number)` — xg 를 비우면 서버가 위치로 계산한다(라이브 입력과 같은 식).
- 볼 것: `DUPLICATE_SUSPECT` 면 이미 기록된 것일 수 있다 — 직원에게 보여 주고, 정말 다른 슈팅이면 `allow_duplicate: true` 로 다시 plan. 골이면 score +1.

### E. 같은 기록이 두 번 들어갔다(중복)
- 확인: `get_timeline` 에서 같은 팀·같은 종류·몇 초 차이 기록 둘을 보여 주고, 어느 쪽을 지울지 직원이 고르게 한다(보통 나중 것).
- op: `delete_event(event_id)`
- 볼 것: 골 중복이면 score −1 이 맞는지. 지운 기록은 `revert_change` 로 되살릴 수 있다.

### F. 하프 시작 시각이 잘못 찍혔다
- 확인: 실제로 그 하프가 시작될 때 **앞 하프 시계**가 몇이었는지(예: 전반이 45+2:30 에 끝나고 바로 후반 시작 표시를 눌렀어야 했다). 진행 중이면 이미 있는 표시만 옮길 수 있다.
- op: `set_period_start(period="2H", previous_period_clock="45+2:30")`
- 볼 것: `PERIOD_SHIFT` — 하프가 바뀌는 기록 수와 표시 시각이 바뀌는 기록 예시. 후반 기록의 경기 시계가 모두 같은 만큼 밀리므로, 후반 기록 시각이 원래 맞았다면 이 절차가 아니다(대표에게 문의).

### G. 기록 시각이 일정하게 몇 초씩 밀려 있다(시계를 늦게/일찍 켬)
- 확인: 어느 하프의 어느 범위인지, 몇 초 늦은지/빠른지(기준이 된 장면 하나를 직원이 영상으로 확인한 값).
- op: `shift_events(half="2H", from_clock="45:00", to_clock="70:00", delta_seconds=-8)` — 한 번에 20건까지라 범위를 나눠 여러 번.
- 볼 것: 옮긴 건수, 하프 밖으로 나가지 않는지. 진행 중 경기의 **지금 시계 자체**가 틀렸다면 그건 운영자가 매치 컨트롤에서 맞춘다(에이전트는 시계를 건드리지 않는다).

### H. 점유 팀이 반대로 / 점유 경계가 늦게 찍혔다
- 확인: 어느 구간인지(`get_timeline` 의 possession_segments 에서 시작·끝 시각으로 고르게 한다), 맞는 팀 또는 맞는 전환 시각.
- op: `set_possession_team(segment_id, team)` 또는 `move_possession_boundary(segment_id=앞 구간, new_end={half, clock})`
- 볼 것: possession 전/후 %. 열린 구간이면 거부(운영자 몫).

### I. 골이 아닌데 골로 / 골인데 슈팅으로 들어갔다
- 확인: 실제 결과(골·유효슈팅·빗나감), 유효슈팅이면 골문 도착 위치.
- op: 골→슈팅 `update_event(id, set={"is_goal": false})`(유효슈팅이 아니었다면 `"is_on_target": false` 도), 슈팅→골 `update_event(id, set={"is_goal": true, "goalmouth_x": .., "goalmouth_y": ..})`(도착 위치가 이미 있으면 생략).
- 볼 것: score ±1.

### J. 공격방향이 잘못 찍혔다
- op: `update_event(event_id, set={"lane": "RIGHT"})` 또는 팀·시각. 지울 때는 `delete_event`.

### K. 경기 이름(대회·라운드·팀 이름)이 틀렸다 — 보관된 경기만
- op: `rename_match(name="[K3 | 28R] 홈팀 vs 어웨이팀")` — 대회 코드가 콘솔에 등록돼 있어야 한다.
- 볼 것: 팀 이름이 바뀌면 FinePlay 전송·카드에 쓰이는 이름도 바뀐다. 팀을 통째로 바꾸는 일이면 대표에게 문의.

## 8. 한 번에 바꾸는 양 · 한도

- plan 하나에 ops 최대 20개, 실제로 바뀌는 행도 최대 20개.
- plan 유효시간 10분. 토큰당 분당 60회 호출(수정 계열 20회), 하루 수정(apply+revert) 40회, 하루 plan 200회.
- 한도를 넘으면 429 — `Retry-After` 초만큼 기다린다. 하루 한도를 다 쓰면 대표에게 문의.

## 9. 모호하면 먼저 물을 질문

- 어느 경기인가요? (대회·라운드·팀 — `list_matches` 결과를 보여 주고 고르게)
- 어느 하프인가요? (전반·후반·연장)
- 그 시각은 **경기 시계**(전광판·매치 컨트롤)인가요, 영상 시각인가요, 콘솔 기록 수정 화면에서 본 시각인가요? (영상 시각이면 경기 시계로 다시, 수정 화면 시각이면 1장 ⚠️)
- 어느 팀인가요? 홈인가요 어웨이인가요? (팀 이름으로 답하면 home_team/away_team 으로 확인)
- 어느 기록인가요? (같은 분에 기록이 여러 개면 목록을 보여 주고 고르게)
- 골인가요, 유효슈팅인가요, 빗나간 슈팅인가요? 자책골인가요?
- 선수 등번호가 몇 번인가요?
- (슈팅 추가) 슈팅 위치는 어디였나요? 골문 어디로 갔나요?
- (진행 중 점수 변경) 운영자에게 알렸나요?

## 10. 대표에게 문의로 끝나는 경우

- 위 절차(A~K)에 없는 정정, 위 질문으로도 값을 정할 수 없을 때.
- 라인업(선수 명단·등번호) 자체가 틀렸을 때, 팀이 통째로 바뀌어야 할 때.
- 점유 구간 지우기·전체 초기화, 경기 생성·삭제·보관·보관 해제, 송출, 잠금, 하이라이트·카드·FPA·FinePlay 전송.
- 풋살·농구 경기(이 API 는 축구 기록만 고친다).
- 서버가 `EDITOR_REJECTED` 등 이 문서에 없는 오류를 돌려줄 때.

## 11. 오류 코드

| 코드 | 뜻 | 할 일 |
|---|---|---|
| BAD_CLOCK · BAD_HALF · CLOCK_OUT_OF_HALF | 시각 표기가 틀림 | 1장 규칙대로 다시 |
| PERIOD_NOT_STARTED · CLOCK_IN_NEXT_PERIOD | 하프가 안 맞음 | 하프를 다시 묻기 |
| NUMBER_NOT_IN_LINEUP · NAME_MISMATCH · NAME_WITHOUT_NUMBER | 선수가 라인업과 다름 | 등번호를 다시 묻기 |
| GOAL_NOT_ON_TARGET · GOALMOUTH_REQUIRED | 골·유효슈팅 관계가 틀림 | 4장 |
| DUPLICATE_SUSPECT | 3초 안에 같은 기록이 있음 | 직원에게 보여 주고 확인 |
| LIVE_FUTURE_TIME · LIVE_TOO_RECENT · LIVE_PERIOD_TRANSITION · LIVE_RENAME · SEGMENT_OPEN | 진행 중 보호 | 6장 |
| EVENT_NOT_FOUND · SEGMENT_NOT_FOUND | id 가 이 경기에 없음 | get_timeline 으로 다시 |
| TOO_MANY_ITEMS | 20건 초과 | 범위를 나누기 |
| stale_plan · new_input_clash (409) | plan 뒤에 기록이 바뀜 | 다시 plan |
| changed_after_apply (409, revert) | 적용 뒤에 또 바뀜 | 지금 기록을 보고 새로 plan |
| 403 | 권한 없음·금지된 일 | 하지 않는다 |

## 12. apply 뒤 직접 다시 해야 할 일

apply 응답 `follow_ups` 에 그대로 나온다. 요약:
- 자동 반영: 결과·요약·우세도·CSV·협업사 API·FinePlay 어드민 조회(최대 3초), 진행 중이면 방송 점수판·오버레이(3초)·실시간 중계 그래픽(60초).
- 자동 아님: 이미 만든 중계 그래픽 보관본(15·30·45분·보관 때 확정본), 골마다 만든 xG 샷맵 그림, FCM 골키퍼 카드, FHL 하이라이트 로그 파일, 녹화 영상 그래픽 편집 프로젝트, 협업사 웹훅.
- 영향 없음: FinePlay 전송(분석 결과·대회 인입은 FLA 기록을 쓰지 않는다).
